---
title: Batch imports
description: Import MCP capabilities with shared bindings, aliases, schemas, and call budgets.
---

Batch imports reduce repetition for one MCP namespace.

## Tool-only batch

```wire
from mcp.tasks.tool {
    max_calls: 6

    bindings {
        workspace_id: input.workspace_id
    }

    tool fetch_task {
        max_calls: 2

        bindings {
            task_id: input.task_id
        }
    }

    tool update_task_status
}
```

The `.tool` namespace accepts only tool items. Shared bindings/budget apply to the batch; item blocks can specialize local bindings, schemas, and `max_calls`.

## Prompt-only batch

```wire
from mcp.tasks.prompt {
    prompt writer_instructions
    prompt review_checklist
}
```

## Resource-only batch

```wire
from mcp.tasks.resource {
    resource project_readme
    resource task_template
}
```

## Mixed batch

```wire
from mcp.tasks {
    prompt writer_instructions
    tool update_task_status
    resource project_readme
}
```

The broader server namespace accepts all three capability kinds.

## Naming

Remote names that contain hyphens are normalized for local references. Use `as` for an explicit local name:

```wire
from mcp.tasks.tool {
    tool fetch-task as fetch_task
}
```

## Binding merge

Shared bindings are merged with item-local bindings. A local value replaces a shared value with the same name and preserves other shared values. `bindings` are runtime expressions, not type declarations.

## Guidance

- Use a batch only when capabilities genuinely share server/scope configuration.
- Prefer individual imports when contracts or authorization scopes differ materially.
- Narrow `max_calls` at the batch, item, deterministic call, and agent usage layers as appropriate.
- Regenerate [MCP lockfiles](/mcp/lockfiles) after changing a batch.
