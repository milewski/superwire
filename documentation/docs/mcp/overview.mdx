description: Understand how MCP servers, tools, resources, and prompts fit into a Superwire workflow.

MCP gives Superwire workflows access to external capabilities. In practice, MCP is where your workflow connects to real systems: APIs, databases, internal services, and curated prompt or content sources.

## Transport and trust

Superwire implements remote MCP over HTTP JSON-RPC. Endpoints must be absolute `http` or `https` URLs without URL user information. `stdio` and other local-process MCP transports are not implemented.

Network authority depends on the component:

| Component | Network authority |
| --- | --- |
| Executor runtime routes (`/execute`, `/validate`, `/graph`) | The operator sets `--mcp-network-policy` to `disabled`, `public-only`, or `trusted` for the whole server. Server configuration defaults to `disabled`; an HTTP request cannot override it. |
| `superwire-cli` | Deliberately uses `trusted`, so CLI discovery and execution can reach reviewed local/private endpoints. |
| `superwire-lsp` | Independently remains no-network unless client initialization explicitly sets `workspaceTrust.networkMcpDiscovery` to `trusted`. |

The executor policies are:

- `disabled`: blocks all outbound MCP networking.
- `public-only`: permits only public `http`/`https` destinations. It resolves hostnames and rejects the endpoint if any literal address or DNS answer is local, private, link-local, multicast, reserved, documentation, or cloud metadata. It pins the approved normalized address set and port in a custom `ureq` resolver.
- `trusted`: also permits local/private HTTP endpoints, but still requires `http`/`https` and rejects URL user information. It does not enable `stdio` or local processes.

For both enabled policies, the HTTP client ignores environment proxies, disables automatic redirects, and rejects redirect responses.

These are endpoint trust and SSRF controls, not a network sandbox. Apply deployment egress controls independently.

Use this section as the mental model:

```text
mcp server -> import capability -> scope with uses -> execute in workflow
```

## Capability types

- `tool`: Callable operation, often used for fetch/create/update behavior.
- `resource`: Read-only content source.
- `prompt`: Reusable prompt template managed by an MCP server.

## Two execution modes

Superwire supports two ways to use MCP tools:

1. **Workflow-owned call** in `dynamic {}` using `call tool.*`.
   - Best for deterministic steps that must always run.
   - Best when runtime values should be bound explicitly.
2. **Model-owned call** inside an `agent` through `uses: [tool.*]`.
   - Best when model judgment decides if a tool is needed.
   - Best for selective retrieval or exploratory reasoning.

## Recommended authoring pattern

1. Declare MCP servers with endpoint and auth headers.
2. Import only needed tools/resources/prompts.
3. Use workflow-owned calls for required operations.
4. Give agents least-privilege `uses` access.
5. Keep outputs typed so downstream steps stay stable.

## Example end-to-end shape

```wire
input {
    task_id: number
}

secrets {
    mcp_token: string
}

mcp tasks {
    endpoint: "https://tools.internal.example.com/mcp"

    headers {
        Authorization: "Bearer {{ secrets.mcp_token }}"
    }
}

tool fetch_task from mcp.tasks.tool.fetch_task
resource writing_style from mcp.tasks.resource.writing_style

dynamic {
    task: call tool.fetch_task {
        bindings {
            task_id: input.task_id
        }
    }
}

agent writer {
    model: model.fast
    uses: [resource.writing_style]
    instruction: "Write a concise update for {{ dynamic.task.title }}."

    output {
        update: string
    }
}
```

This internal-server example requires `trusted` when the endpoint resolves to a local/private address. The CLI already uses `trusted`; executor runtime routes and LSP discovery use their independent gates described above.

This pattern keeps deterministic fetches in the workflow and model creativity in the agent.
