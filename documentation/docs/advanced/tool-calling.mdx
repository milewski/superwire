## Workflow-owned calls

Use `dynamic` plus `call tool.name` when the operation is required and its position in the graph is fixed. Supply application-owned scope through `bindings`; supply ordinary call input through `input`.

## Model-owned calls

Expose a tool through agent `uses` when model judgment determines whether/how to call it. The model receives only listed tools, prompts, and resources.

## Bound every layer

`max_calls` can apply at import, batch, deterministic call, and agent usage scopes. Use the narrowest budget that still supports the workflow. Also bound request concurrency, provider retries, timeout, rate, and domain operations outside the prompt.

## Domain guardrails

Superwire tool scope does not replace:

- authentication and authorization inside the MCP server;
- tenant scoping derived from trusted bindings;
- idempotency for writes;
- transactions and uniqueness constraints;
- human approval for destructive work;
- rate limits, audit logs, and cost controls.

## Validate and observe

Declare input/output schemas, generate/review MCP locks, and consume public tool/MCP validation/call event metadata. These events report names, durations, diagnostics, and result shapes—not argument values, schemas, or returned payloads. A model tool call can fail even when source validation succeeds because remote availability and returned data are runtime concerns.

See [MCP tools](/mcp/tools), [MCP lockfiles](/mcp/lockfiles), and [Streaming and events](/api-reference/streaming-events).
