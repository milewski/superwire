## Independent graph nodes

<ParallelWorkflow />

`risks` and `actions` are ready together because neither references the other. `plan` becomes ready only after both values exist.

Superwire derives this graph from references; source order does not serialize independent agents.

## Looped nodes

<LoopWorkflow />

Each loop iteration is independently schedulable after its upstream values are ready. Results are returned in input order even if executions complete out of order.

## Limit concurrency

HTTP execution option:

```json
{
  "options": {
    "max_concurrency": 2
  }
}
```

The default is `5`. The runtime uses an effective minimum of one. The same limiter covers runtime work scheduled concurrently; choose a value that respects provider/MCP rate limits and deployment capacity.

`superwire-cli workflow run` currently uses a concurrency value of `10` internally and does not expose a CLI flag for it.

## Practical design

- Split independent responsibilities rather than creating artificial sequential chains.
- Preserve required order with explicit value/context/tool dependencies.
- Use loops for homogeneous typed collections.
- Aggregate only after fan-out when synthesis needs every result.
- Keep write operations idempotent; concurrency can expose domain races the workflow type system cannot prevent.
- Use SSE plan/loop/agent events to explain actual scheduling.
