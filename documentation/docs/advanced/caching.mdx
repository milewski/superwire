Caching stores each completed agent execution as both its structured output and its provider context. It does not cache the final HTTP wrapper independently.

## Drivers

| Driver | Use |
| --- | --- |
| `in-memory` | Local development or one executor process; lost on exit and not shared. |
| `redis` | Shared cache across executor processes. |

The executor defaults to in-memory with a `1h` TTL.

```bash
superwire-executor --cache-driver in-memory --cache-ttl 1h
```

```bash
superwire-executor \
  --cache-driver redis \
  --redis-host redis.internal:6379 \
  --redis-password "$REDIS_PASSWORD" \
  --redis-database 0 \
  --cache-ttl 30m
```

Omit `--redis-password` only for an isolated development instance that intentionally has no authentication.

## Stored data and Redis security

Redis entries are JSON objects containing `output` and `context`. For the Cersei provider, `context` is serialized message history: it can include prior conversation, the current rendered user prompt (including interpolated runtime values or asset content), and assistant output. A Redis dump therefore exposes substantially more than the final workflow output.

Values are serialized without application-layer encryption, and the current cache connection uses `redis://`. For a production Redis cache:

- isolate it on a private network and require Redis authentication/firewall policy;
- provide transport encryption through trusted network infrastructure or a TLS tunnel/proxy;
- encrypt Redis persistence files and backups with deployment-managed controls;
- use tenant/authorization-aware cache keys, a short TTL, and explicit invalidation;
- disable shared caching (`use_cache: false` or `--no-cache`) when prompts/context contain secrets, regulated data, or data that must not persist.

The hashed Redis key hides the client cache identifier; it does not encrypt or redact the stored value.

## HTTP cache scope

HTTP cache access requires a non-empty client key:

```json
{
  "workflow_source_base64": "BASE64_SOURCE",
  "input": {"name": "Ada"},
  "secrets": {"api_key": "replace-at-runtime"},
  "options": {
    "cache_key": "tenant-1:conversation-42",
    "use_cache": true
  }
}
```

`use_cache` defaults to true, but no key means no HTTP cache reads or writes. Different keys never share entries.

Choose keys that include every application boundary required to prevent inappropriate reuse, such as tenant, conversation, user permission version, or workflow revision. Do not put credentials in a key.

## Disable per request

```json
{
  "workflow_source_base64": "BASE64_SOURCE",
  "options": {
    "cache_key": "tenant-1:conversation-42",
    "use_cache": false
  }
}
```

## Rotate or delete

Changing the key starts a fresh cache scope but leaves old entries until TTL/eviction. Delete entries explicitly:

```bash
curl --fail-with-body http://localhost:13703/cache/invalidate \
  -H 'Content-Type: application/json' \
  -d '{"cache_key":"tenant-1:conversation-42"}'
```

Response:

```json
{
  "purged_entries": 3
}
```

The Playground purge control rotates the tab key; it does not call this deletion route.

## Degraded cache behavior

Cache reads and writes are availability aids, not execution correctness dependencies:

- a read failure bypasses cache, executes the agent, and emits `cache_degraded` with `subject.operation: "read"`;
- a write failure returns the fresh result and emits the warning with operation `write`;
- an invalidation-driver failure returns HTTP 503 `cache_unavailable` with cache operation `purge`; it never reports an unconfirmed deletion as successful.

Read/write degradation emits a `cache_degraded` warning with `code: "cache_unavailable"`, `stage: "cache"`, and `severity: "warning"` while execution continues. Invalidation is different: its typed diagnostic has error severity and retryability `safe`, and the response contains no `purged_entries`. A successful zero count means the purge completed and found no matching entries.

## CLI cache

`superwire-cli workflow run` uses a local cache session and defaults to in-memory caching. Configure `--cache-driver`, `--cache-ttl`, or `--no-cache`. CLI runs do not use the HTTP `options.cache_key` contract.

## Correctness guidance

- Cache only deterministic-enough agent boundaries for the application's needs.
- Rotate/invalidate after workflow/model/tool behavior changes when stale output is unsafe.
- Apply the [stored-data controls](#stored-data-and-redis-security) before using Redis.
- Do not assume cache hits skip all validation; source and runtime configuration still form the execution contract.
