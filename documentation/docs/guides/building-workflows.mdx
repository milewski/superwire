## 1. Start at the boundary

Write the caller contract before prompts:

```wire
input {
    name: string
}

secrets {
    api_key: string
}
```

Decide which values are public input, which are sensitive runtime secrets, and what exact final JSON shape the application consumes.

## 2. Make one step work

<HelloWorkflow />

Validate and format before execution:

```bash
superwire-cli workflow check hello.wire
superwire-cli fmt hello.wire
```

## 3. Add typed data flow

<ChainWorkflow />

References are dependencies. Add a second agent only when its model call has a distinct responsibility and consumes a smaller typed result.

## 4. Scale deliberately

- Split independent work so the graph can schedule it concurrently.
- Use a loop for a typed array of similar items.
- Set `options.max_concurrency` at the HTTP boundary.
- Add an aggregation agent only when a model must synthesize fan-out results.
- Add a cache key only when reuse semantics are clear.

See [Parallel and looped work](/examples/parallel-processing).

## 5. Add external capabilities

<McpTaskWorkflow />

Separate model-visible tool `input` from trusted workflow `bindings`, narrow `max_calls`, and generate a lock:

```bash
superwire-cli workflow vars mcp-task.wire --output .wire.vars
superwire-cli workflow lock mcp-task.wire --vars-file .wire.vars
```

## Review checklist

- Runtime JSON matches `input` and `secrets` types.
- Credentials are not hardcoded or interpolated into model instructions.
- Provider driver, endpoint, model ID, and `wire_api` match the backend.
- Every agent has a model, instruction, and object-shaped output.
- Schema reuse appears as typed output fields, not scalar agent output.
- Dependencies are visible through references/context/tool calls.
- Every model-owned capability is in `uses` and bounded where practical.
- Files use Chat Completions mode.
- CLI check/format and canonical fixture CI pass.
