This checked fixture demonstrates both ownership modes:

1. The tool declaration binds `task_id` from trusted workflow input. `dynamic.task` calls it deterministically.
2. The writer also receives scoped model-owned access through `uses`, limited to one call for that agent and two calls for the workflow import.

The placeholder `example.test` endpoint is intentionally non-routable. Replace it with your MCP server, supply runtime secrets, and generate a lock before execution:

```bash
superwire-cli workflow vars mcp-task.wire --output .wire.vars
superwire-cli workflow lock mcp-task.wire \
  --vars-file .wire.vars \
  --output superwire.lock
```

The CLI performs lock discovery with trusted network access, including private or local HTTP endpoints. Run it only for reviewed workflow source from a process with appropriately restricted egress, and do not commit a real token in `.wire.vars`. See [MCP lockfiles](/mcp/lockfiles).
