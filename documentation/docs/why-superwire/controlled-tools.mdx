Tools turn a model step into an application actor. Scope and ownership therefore belong in the workflow contract, not only in a prompt.

## Checked pattern

<McpTaskWorkflow />

The fixture contains both boundaries:

- `dynamic.task` is a workflow-owned call. The fetch always occurs at that graph node, and trusted `task_id` comes from a binding.
- `agent.writer` may call the same tool through `uses`, but only that agent receives it and its local call budget is one.

## Least privilege

An imported tool is not automatically available to every agent. A classification step can have no tools; a research step can receive read-only retrieval; a later write step can receive one narrowly bounded mutation tool.

## Fixed operation versus model judgment

Use a workflow-owned call when the application requires the operation or order. Use model ownership when deciding whether/how to call is part of the reasoning task.

Do not write `{{ task }}` for a dynamic value. Runtime computed fields use their namespace, such as `{{ dynamic.task }}` or `{{ dynamic.task.title }}`.

## What remains outside Superwire

Tool scope does not replace authorization, tenant isolation, idempotency, transactions, rate limits, audit logs, or human approval. Those controls remain in the application/MCP implementation.

Review [MCP tools](/mcp/tools), [Tool calling safety](/advanced/tool-calling), and [MCP lockfiles](/mcp/lockfiles) before enabling write capabilities.
