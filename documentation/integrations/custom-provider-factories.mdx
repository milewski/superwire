## Why this abstraction matters

The DSL provider block is just structured data:

```txt
provider my_backend {
    driver: "internal"
    region: "us-east-1"
    api_key: secrets.internal_api_key
    models: ["research-v1"]
}
```

Your factory decides what those properties mean at execution time.

## Common pattern

1. evaluate provider settings from the workflow
2. inspect `driver` and related keys
3. construct a concrete provider instance
4. wrap it with `DynamicProvider::new(...)`

## Testing custom factories

Use `WorkflowRuntime::new(MyProviderFactory)` in tests and drive it with small workflows that assert:

- provider selection by name
- setting translation
- model selection
- output wiring
